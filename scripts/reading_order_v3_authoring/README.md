# Reading Order v3 clean-room authoring contract

**SAFE FOR ISOLATED AUTHOR TO READ**

This directory is the complete candidate-independent interface for authoring a new Reading Order v3 corpus. An isolated author should not need any historical held-out corpus, historical corpus validator, calibration fixture, candidate diagnostic, qualification evidence, or forensic evidence to create and structurally validate a new corpus.

This kit validates only schema, sealed-file integrity, input/annotation consistency, and abstract v3 authoring coverage. It does **not** import or execute the Reading Order candidate, run OCR, evaluate reachability, score candidate output, or authorize qualification.

## Corpus layout

A corpus root contains exactly:

- `corpus-design.json`;
- one source file, RGB PNG image, input JSON, and annotation JSON for each declared page;
- `manifest.json`, generated by this kit.

Role files may use any safe relative path declared by the design. Source files have no prescribed format. Images must be decodable RGB PNG files because the future sealed-input runtime contract consumes verified PNG bytes as RGB pixels. Width and height are not fixed; the PNG dimensions must exactly match the page input dimensions.

No undeclared file is permitted in the sealed corpus root. `manifest.json` is excluded from its own inventory.

## Identity and page identifiers

`corpusId`, `version`, and `pageId` values are chosen by the new corpus author. They are not tied to any historical identity, version, page count, or page numbering scheme.

- `corpusId` and `version`: 1–128 characters, starting with an ASCII letter or digit and then using letters, digits, `.`, `_`, `+`, or `-`.
- `pageId`: 1–128 characters, starting with an ASCII letter or digit and then using letters, digits, `.`, `_`, or `-`.
- page IDs must be unique within the design.

The kit does not impose a historical page count or historical pair/layout minimum.

## `corpus-design.json`

Schema version: `reading-order-v3-authoring-design-v1`.

Required top-level fields:

```json
{
  "schemaVersion": "reading-order-v3-authoring-design-v1",
  "corpusId": "future-reading-order-corpus",
  "version": "draft-a",
  "authorshipBoundary": "isolated-candidate-independent-v3",
  "provenanceDeclaration": {
    "priorHeldoutEvidenceInspected": false,
    "calibrationOutputsInspected": false,
    "candidateDiagnosticsInspected": false,
    "candidateExecuted": false,
    "qualificationExecuted": false,
    "annotationsAdaptedToCandidateOutput": false
  },
  "pages": []
}
```

`provenanceDeclaration` is an explicit author declaration. The validator checks that the declaration is present and has the required clean-room values; it cannot independently prove the truth of the declaration.

Each page record has exactly these fields:

```json
{
  "pageId": "page-alpha",
  "source": "sources/page-alpha.source",
  "image": "images/page-alpha.png",
  "input": "inputs/page-alpha.json",
  "annotation": "annotations/page-alpha.json",
  "authoringCoverage": {
    "positiveFamilies": ["c1-boundary-positive"],
    "primaryPositiveFamily": "c1-boundary-positive",
    "c3Rejection": false
  }
}
```

All role paths are safe normalized POSIX-relative paths. Paths must be unique across all page roles. `corpus-design.json` and `manifest.json` are reserved and cannot be used as role paths.

## Abstract v3 authoring coverage

The positive authoring families are exactly:

- `c1-boundary-positive`
- `c2-gutter-bridge`
- `c2-ambiguous-overlap-bridge`
- `c2-pair-precedence-slot`
- `c3-positive-recovery`
- `b1-horizontal`
- `b1-vertical`
- `b1-mixed-orientation`

Every positive family requires at least one **dedicated** page. A page is dedicated only when `positiveFamilies` contains exactly one family and `primaryPositiveFamily` names that same family. A combined page may declare multiple positive families, but it does not satisfy any dedicated-family requirement. This keeps each positive family independently authored rather than making all positive coverage depend on one combined case.

C3 negative authoring coverage is page-level. Set `c3Rejection: true` on a page that is intended to provide generic C3 rejection coverage. The validator reports `c3_rejection_pages` as unique page IDs, so one page counts at most once. This clean-room contract makes no category-specific or pair-local causal claim about the rejection.

The kit requires nonempty page-level C3 rejection coverage but deliberately carries no historical C3 page minimum.

## Input schema

Schema version: `reading-order-v3-authoring-input-v1`.

```json
{
  "schemaVersion": "reading-order-v3-authoring-input-v1",
  "pageId": "page-alpha",
  "width": 800,
  "height": 600,
  "regions": [
    {
      "regionId": "region-a",
      "sourceIndex": 0,
      "lines": [[[10, 10], [20, 10], [20, 20], [10, 20]]],
      "angle": 0.0
    }
  ]
}
```

Generic input invariants:

- width and height are positive integers;
- regions are nonempty;
- `regionId` values and `sourceIndex` values are unique;
- `sourceIndex` is contiguous from zero;
- each line is one four-point integer quadrilateral inside the declared page bounds;
- angle is a finite number.

## Annotation schema

Schema version: `reading-order-v3-authoring-annotation-v1`.

```json
{
  "schemaVersion": "reading-order-v3-authoring-annotation-v1",
  "pageId": "page-alpha",
  "readingOrder": ["region-a"],
  "unscoredRegionIds": []
}
```

`readingOrder` and `unscoredRegionIds` must each be duplicate-free and must not overlap. Their union must equal the exact input-region inventory for the page. The design, input, and annotation must use the same `pageId`.

## Manifest and inventory

Schema version: `reading-order-v3-authoring-manifest-v1`.

Do not hand-maintain hashes. Generate the manifest after all authoring files are final:

```text
python -m scripts.reading_order_v3_authoring build-manifest /path/to/new-corpus
```

The generated manifest binds:

- corpus identity and version;
- `corpus-design.json` SHA-256;
- each page ID to its source/image/input/annotation path and SHA-256;
- the exact file inventory, with byte length and SHA-256 for every sealed file except `manifest.json` itself.

Any missing file, extra file, changed bytes, role-path change, or stale hash invalidates the corpus.

Validate the complete sealed corpus with:

```text
python -m scripts.reading_order_v3_authoring validate /path/to/new-corpus
```

Library users may call `build_manifest`, `write_manifest`, `validate_corpus`, `sha256_path`, and `write_canonical_json` from `scripts.reading_order_v3_authoring`.

## Paths an isolated author must not open

The isolated author should stay inside this clean-room directory and the new corpus directory. Do not open:

- `assets/reading-order-v2/heldout*/`
- `scripts/reading_order_v2/validate_corpus.py`
- `tests/reading_order_post_v2_calibration/`
- `backend/src/mangasensei/ocr/diagnostics/reading_order_post_v2_calibration.py`
- `scripts/reading_order_post_v2_qualification/`
- qualification workflow outputs or forensic evidence directories

These paths are listed only as isolation boundaries. This document intentionally does not reproduce or explain their corpus-specific constraints, candidate behavior, calibration observations, or qualification results.

## Non-goals

Passing this validator means only that the new corpus is structurally well-formed, sealed consistently, and satisfies candidate-independent abstract authoring coverage. It is not evidence of candidate reachability, quality, determinism, generalization, or qualification readiness, and it does not create or consume a qualification identity.
